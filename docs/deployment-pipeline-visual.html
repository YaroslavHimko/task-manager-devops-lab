01 / Big picture

The delivery pipeline

Think of a pipeline as a sequence of transformations. Code becomes compiled files, then Docker images, then containers, which Kubernetes manages as Pods. A CI/CD platform can automate some or all of these steps.

The complete path from code to users

Developer/build Package/publish Run and expose
BUILD

Docker image

A reusable, versioned package: compiled application, runtime dependencies, and startup command. Not a running process.

RUN

Container

A running instance of an image. It has a process, filesystem view, environment, and network.

ORCHESTRATE

Kubernetes Pod

The unit Kubernetes schedules. In this lab, each Pod holds one running application container.

06 / Hands-on stage 3

Build Docker images and run both services

One Dockerfile for the backend and another for the frontend. Both use multi-stage builds: large build tools are discarded before the smaller runtime image is created.

Two separate image builds

Dockerfile vs Docker image

Dockerfile: recipe for building a package.

Image: built package, e.g. interview-api:v1.

Container: running instance of that image.

Start the application with Docker Compose

Compose creates a network and starts two containers from two images.

3
UBUNTU · project root
docker compose up --build -d

docker compose ps
docker images
curl -i http://localhost:8080/api/health
curl http://localhost:8080/api/tasks
✓ Expected: API health returns JSON like {"status":"healthy"}. Browse to http://localhost:8080, add a task, and see it appear.
Why only one exposed port? Compose maps localhost:8080 → frontend:80. Nginx reaches api:8080 on the internal Docker network. No need to publish the API container's port to your laptop.
UBUNTU · investigate and stop
docker compose logs --tail=40 api
docker compose exec frontend sh
# type 'exit' to leave the container

docker compose down
See the key Compose configuration
compose.yaml · included in the project
services:
  api:
    build: ./api
    image: interview-api:v1
    environment:
      ASPNETCORE_URLS: http://+:8080

  frontend:
    build: ./frontend
    image: interview-frontend:v1
    depends_on:
      - api
    ports:
      - "8080:80"

Note: depends_on controls startup order, not application readiness. Real production setups should have proper health checks and retry handling.

See the Nginx reverse-proxy rule
frontend/nginx.conf
location /api/ {
    proxy_pass http://api:8080;
}
location / {
    try_files $uri $uri/ /index.html;
}

This lets the browser use relative paths and avoids configuring CORS for two different origins in this lab.

07 / Hands-on stage 4

Deploy the same images to Kubernetes

Kubernetes isn't a replacement for your application or Docker images. It is a control system that creates Pods, monitors health, and keeps the number of replicas you request.

What your Kubernetes YAML creates

The lab deliberately uses one API replica because its task data lives in memory. Two API replicas would have inconsistent task lists. A real application should use a shared database.

DESIRED STATE

Deployment

Asks for replicas and specifies which container image/version to run. Supports updates and rollback history.

EXECUTION

Pod

Hosts a running application container. Pods can be replaced and receive new IP addresses.

DISCOVERY

Service

Gives the Pods a stable network address and routes requests to Pods that are ready.

Create a local cluster, load your images, deploy

Install kind and kubectl in Ubuntu first.

4
UBUNTU · project root
# Rebuild if needed; images are stored in Docker
# Stop Compose if it still holds port 8080
docker compose build
docker compose down

kind create cluster --name interview-lab --wait 120s
kind load docker-image interview-api:v1 interview-frontend:v1 --name interview-lab

kubectl apply -f k8s/
kubectl rollout status deployment/api --timeout=180s
kubectl rollout status deployment/frontend --timeout=180s
kubectl get deployments,pods,services
Why kind load? The Docker images on your laptop aren't automatically available inside the kind cluster's node. Loading them makes them available without publishing to a registry.
UBUNTU · terminal stays open
kubectl port-forward service/frontend 8080:80
✓ Expected: Open http://localhost:8080 and use the same app, now managed by Kubernetes. Keep port-forward running in its terminal.

What the YAML really means

YAML propertyPlain-English meaning
kind: DeploymentManage and replace Pods to match desired state.
replicas: 2Keep two frontend Pods running, when possible.
image: interview-frontend:v1Which package each Pod should run.
selector: app: frontendHow the Service finds the right Pods.
readinessProbeOnly send normal Service traffic after the Pod is ready.
livenessProbeRestart an unhealthy container if liveness checks keep failing.
08 / Hands-on stage 5

Release version 2, then roll back

This is a particularly valuable interview demonstration. An image tag is a version of your deployed package; Kubernetes can roll from one version to another.

Edit a visible string in api/Program.cs

Change one of the three initially seeded tasks so the new API response is obvious.

Build a new API image

Give it v2, not v1. Different tags make releases explicit.

Load that image into kind

The Kubernetes node must have access to the new image.

Update the Deployment and watch

Kubernetes creates the replacement Pod and performs the rollout.

Undo if something goes wrong

Rolling back restores the previous image configuration.

UBUNTU · project root
docker build -t interview-api:v2 ./api
kind load docker-image interview-api:v2 --name interview-lab
kubectl set image deployment/api api=interview-api:v2
kubectl rollout status deployment/api
kubectl rollout history deployment/api

# Revert the deployment image to the previous revision
kubectl rollout undo deployment/api
kubectl rollout status deployment/api
Demo limitation: This API stores tasks in process memory. Deploying or rolling back restarts the process and resets that data. Also, with one API replica, availability during a rollout is not guaranteed. Production systems use persistent shared storage and appropriate rollout strategies.

How to inspect after a rollout

kubectl
kubectl get pods -o wide
kubectl describe deployment/api
kubectl logs deployment/api

Try changing replica count

kubectl
kubectl scale deployment/frontend --replicas=3
kubectl get pods -l app=frontend

Scaling the frontend is safe in this lab; don't scale the in-memory API.

09 / Optional team workflow

How a real CI/CD pipeline differs from the local lab

Teams usually don't manually build on developers' machines and load images into kind. A CI service builds and checks packages, publishes them to a registry, then a separate deployment stage updates a shared cluster.

One machine. No registry required.

Use this route first. It is free, repeatable, and matches every command in the sample project.

GitHub Actions + registry + shared Kubernetes cluster

1. Developer pushes code to GitHub

Git provides traceability and a commit SHA that identifies exactly what changed.

2. CI runner builds and verifies

GitHub Actions executes Docker builds, which run dotnet publish and ng build. Add separate dotnet test / frontend tests before calling the pipeline fully tested.

3. Publish versioned images to GHCR

Example: ghcr.io/OWNER/interview-api:COMMIT_SHA. The cluster needs access to images and any required credentials.

4. Deploy exact versions

A deployment tool (GitOps, Helm, kubectl, or an orchestrated CI job) updates image tags, waits for readiness, and supports rollback.

Security note: Never commit cluster kubeconfig files, passwords, or registry tokens. A real deployment stage needs a controlled authentication method, plus HTTPS, ingress, persistent database, and application secrets.

The example GitHub Actions file included with this guide

.github/workflows/container-publish.yml builds the two Docker images on pushes to main and publishes them to GitHub Container Registry using the GitHub-provided token. This is an optional demonstration and doesn't automatically update your Kubernetes cluster.

Example production image update · requires an accessible cluster and image permissions
kubectl set image deployment/api api=ghcr.io/OWNER/interview-api:COMMIT_SHA
kubectl set image deployment/frontend frontend=ghcr.io/OWNER/interview-frontend:COMMIT_SHA
kubectl rollout status deployment/api
kubectl rollout status deployment/frontend

Replace OWNER and COMMIT_SHA with real values. This is not a command to run against the default kind lab unless that cluster can pull the registry images.

10 / Operating the app

Troubleshooting, from the browser backward

Learn to follow the request path and ask which hop failed. It's more effective than randomly restarting services.

Angular page doesn't open
Check docker compose ps, docker compose logs frontend, or kubectl get pods -l app=frontend. Make sure port-forward is still running.
Page opens, but API returns 502
Nginx cannot reach an upstream. Check API logs, api Service, endpoints, container readiness, and port 8080.
Pod shows ImagePullBackOff
Check the image tag. In kind, run kind load docker-image ... --name interview-lab; for a registry, check credentials and access permissions.
Pod shows CrashLoopBackOff
Container repeatedly crashes. Run kubectl logs deployment/api --previous (when available), then inspect events with kubectl describe pod ....
Pod is running, but not Ready
Inspect readiness probes and app startup. kubectl describe pod ... shows probe failure events. A running process isn't necessarily ready for traffic.
Tasks disappear after an update
Expected in this demonstration: task data is only held in the .NET process's memory, not a persistent database.
UBUNTU · diagnostic commands
kubectl get pods -o wide
kubectl describe deployment/api
kubectl logs deployment/api --tail=100
kubectl get service api
kubectl get endpointslice -l kubernetes.io/service-name=api
kubectl exec deployment/frontend -- wget -qO- http://api:8080/api/health
kubectl rollout history deployment/api
My diagnostic sequence: Browser URL → frontend container → Nginx proxy → api Service → API Pod → health endpoint → API logs. Identify the first failing hop.

Five interview questions you should answer aloud

1. Why would you use Docker for a .NET application?

To package the application with the correct runtime dependencies and startup configuration in a reproducible image. This reduces environment inconsistencies and allows the same image to be tested and deployed across environments. It doesn't replace automated testing, security, or configuration management.

2. Why is Nginx used for Angular instead of Node.js?

The production Angular build emits static assets. Nginx serves them efficiently and reverse-proxies /api to ASP.NET. Node.js is a build tool here, not a runtime requirement for the compiled SPA.

3. What does Kubernetes do when an API Pod crashes?

The kubelet can restart the container within the Pod according to restart policy; a Deployment's ReplicaSet also maintains the desired number of Pods. Liveness probes can trigger a restart. Kubernetes does not automatically fix underlying application bugs.

4. How would you perform a safe update?

Build a uniquely tagged image, test it, make it available to the cluster, update the Deployment to that image, watch rollout readiness, monitor errors, and roll back to a previous revision if required. For real services, add tests, health probes, persistent data, and an appropriate rollout strategy.

5. What's the difference between CI and CD?

CI automatically checks and builds changes. CD can mean Continuous Delivery (a deployable artifact is prepared, with release potentially requiring approval) or Continuous Deployment (releases go automatically to production). A workflow that only pushes images to a registry is not a complete deployment pipeline.
